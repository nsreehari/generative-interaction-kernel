A Governed Interaction Architecture for Human-Agent Systems

From agent-generated domain data to validated UI and controlled execution · Technical position paper · 2026
Thesis. Humans and agents should use one governed interaction architecture instead of separate application paths. Agents return schema-validated domain data; host code turns that data into UI and allowed actions; every participant receives a role-appropriate view of the same authoritative state; and a separate control plane determines who may view, propose, delegate, approve, or execute.

1. The Semantic Split

Most agentic systems give humans and agents different application models. Humans receive screens, forms, dashboards, and approval dialogs. Agents receive prompts, APIs, tools, and loosely structured context. Each path develops its own representation of state, available action, progress, and policy. A recommendation described in prose may not correspond to an executable operation; an API call may bypass the interaction contract visible to a human; and generated presentation may imply meaning the runtime cannot enforce.

Adding orchestration does not close this split. Passing text among agents coordinates conversation, but it does not define shared schemas, valid state changes, or permissions. The system needs one state and event model so that the same request maps to the same operation whether it comes from a person, an agent, or an API.

One authoritative state; closed domain schemas; validated transformations; role-specific views; explicit permissions; auditable external actions.

2. From Generated Responses to Semantic Composition

These models make different engineering tradeoffs. Agent-User Interaction (AG-UI) protocols can turn an agent response into interactive components, making complex data easier to inspect and act on than prose alone. A semantic layer solves a separate problem: it maps source data into stable domain objects, relationships, and actions that screens, agents, and services can interpret consistently. The key design choice is the contract that crosses the agent-host boundary: prose, UI instructions, a fixed template, or validated domain data.

Shift the agent-host contract from inferred prose and UI instructions to validated domain data

Combining interactive delivery with a domain contract gives the host reusable, validated data instead of a one-off screen description. The host can render that data for a user’s task and device, apply its accessibility and interaction standards, or send a machine-readable view to another service. This improves consistency and clarity, reduces duplicated interpretation code, and can shorten the path from analysis to decision.

Engineering boundary. The agent builds a response from allowed domain types; the host validates the data and turns it into UI or machine-readable output.

4. Shared State and Event Runtime

The core runtime is a transport-agnostic state machine. Screens, conversations, agent protocols, and devices all send validated events to the same state store. Each event produces updated state and, when needed, requests for external work:

Runtime contract. applyEvent(state, event) → { state, effectRequests }

State stores domain records, interaction progress, proposals, approvals, results, and audit links. An adaptive workflow can also store hypotheses, failed attempts, branches, or intermediate evidence as named records when the application needs them. These are application-level choices, not built-in runtime concepts. Human and agent requests pass through the same schema and permission checks. Network calls, models, and tools run in effect handlers; their results return as validated events. This keeps state replay reproducible even though external systems are not deterministic.

Each view is a permission boundary, not a separate copy of the application. The human view is designed for comprehension and predictable interaction. The agent API exposes only the data and operations granted to that agent. The administrative view exposes trusted identity, policy, and lifecycle controls. A transport can carry one of these views, but it cannot add permissions.

5. Domain Types and Validated Transformation

Agents are most useful when they work at the level of domain meaning: investigate this incident, construct the attack path, explain this timeline, or propose remediation. They should not need to choose UI components, mutate application state directly, or generate unrestricted tool calls.

A declarative interaction specification defines a sequence of transformation stages. Each stage accepts a closed set of domain types and validates them against a schema. A named transformer converts valid input from one stage into valid output for the next:

Transformation pipeline. domainData → validated transforms → runtime state, UI, and actions

An attack path is domain data; an infinite canvas is one way to display it. The same timeline can be a visual sequence for a person and a structured event list for another agent. Analyze and refresh are runtime commands, not new domain types. Validators check facts, required fields, ordering, and coverage before the host renders or executes anything.

Schemas alone are not enough to expose a safe agent API. The contract also declares valid targets, intents, goals, and constraints. Application code still owns operation schemas and handlers. Agent guidance can evolve with the domain contract, but prose never becomes executable permission.

Policy-controlled adaptation

A fixed specification keeps its original structure. An adaptive specification allows only policy-approved structural changes and records each accepted change in state and checkpoints. An agent can add a hypothesis, link it to evidence, open an attack-path branch, record an unsuccessful attempt, or add the next investigation choice. These changes become shared, queryable records instead of private reasoning left in a transcript.

GraphQuestion answeredArchitectural role
Dependency graphGiven a goal or end state, what prerequisites must be achieved?Works backward from the goal, exposes required subgoals and dependencies, then schedules ready work toward completion.
Consequence graphGiven current state, what has become unlocked or activated?Works forward from achieved facts or changes and identifies newly enabled work that can now be pursued.
Exploratory graphGiven current state and several available paths, which path should be tried next?Uses policy to choose among unlocked paths, records outcomes, and supports backtracking when a pursued path fails.

The graphs serve different runtime decisions. A dependency graph works backward from the goal to calculate missing prerequisites. A consequence graph works forward from current state to identify newly available work. An exploratory graph chooses among several valid next steps. Policy filters and ranks the options; execution returns evidence; and a failed attempt is recorded before the runtime selects another eligible branch.

attack-path exploration
To reach a crown-jewel asset, the dependency graph may require initial access, credential acquisition, privilege escalation, and lateral movement. When credentials are discovered, the consequence graph activates the identities, services, and movement opportunities those credentials enable. The exploratory graph chooses an allowed hypothesis, such as an exposed service rather than phishing. If that path is disproven, it records the failed branch, returns to the last viable choice point, and pursues another policy-eligible hypothesis.

Graph decisions do not grant execution permission. Structure policy controls which hypotheses, relationships, and runtime operations an adaptive specification may add. Tool calls and external actions still require proposal validation, admission, and controlled execution. The state machine may recalculate readiness as graph state changes, but the dependency graph only describes required work; it does not authorize that work.

Transformation contract. Rendering may change structure and presentation, but it must preserve domain IDs, ownership, input and output schemas, source references, and declared purpose. Generated data never bypasses final validation.

6. Agent Proposal and Host Application

The runtime exposes a deliberately small action API: assign, derive, emit, invoke, route, and confirm. High-level intent must compile to these inspectable operations rather than arbitrary generated code.

When the host receives a proposal, it makes four separate decisions before any requested change becomes authoritative:

DecisionQuestion answered
AuthorizationMay this actor request this operation?
AdmissionIs this proposal valid for the current target, revision, state, and governing policy?
Application dispositionMay it apply automatically, remain deferred, or require trusted approval?
ApplicationMay the trusted authority perform the resulting transition now?

The core state machine applies local UI events immediately. Named effect handlers perform model calls, network requests, storage access, and device operations outside that state machine. The host owns credentials, service registrations, endpoint policy, queues, request and response validation, policy checks, timeouts, and execution limits. Provider output remains untrusted until it passes the declared response schema. Even when policy allows automatic application, the host remains responsible for the change and records it in the audit trail.

Runtime construction is reproducible: buildRuntime(spec, domainData, context) → interactionProgram. The same immutable inputs produce the same program. Context may select an internal workflow or UI, but it cannot change domain IDs, permissions, or the application contract.

7. Multi-Agent Operational Postures

Multi-agent composition benefits from distinguishing how a participant approaches a problem from what it can do and what it is authorized to do. Red, Blue, and Green are useful generalized operational postures:

Red · Challenge and discover

Adopts an adversarial perspective, tests assumptions, explores exposure, and establishes whether a weakness is reachable or exploitable.

Blue · Understand and defend

Observes, classifies, correlates, investigates, explains, detects, and recommends defensive response from available evidence.

Green · Improve and restore

Prioritizes corrective change, proposes hardening and remediation, reduces exposure, and measures restored resilience.

The postures form a governed learning loop: challenge reveals pressure, observation establishes meaning, and improvement changes the system before it is challenged again. They are not security privileges and need not be permanent identities. A participant may adopt one or more postures for a bounded goal.

Red is not merely a Blue workflow with adversarial prompts

In security systems, Red frequently becomes a distinct operating class. Blue work commonly begins with known signals such as alerts, incidents, telemetry, vulnerabilities, or posture findings and follows bounded investigative or defensive tasks. Red work searches for what defenders do not yet know. It is iterative and exploratory: observe, form a hypothesis, test it, record the result, and choose the next test. It may run for extended periods, branch across possible attack paths, combine individually minor weaknesses, and produce no confirmed finding.

This distinction belongs primarily to the domain and activity model. A Red agent can use an adaptive specification to add hypotheses and attack-path branches as it explores. The dependency graph tracks the desired end state and missing prerequisites. The consequence graph identifies newly available work as facts are established. The exploratory graph selects, tests, and backtracks across alternative hypotheses. Accepted additions and results enter shared state, allowing humans and Blue or Green participants to inspect the same investigation through their own role-specific views.

That autonomy is limited by the domain schema and active policy. It does not require storing every internal thought, and it does not move offensive execution into the graph. The contract decides which hypotheses, attempts, observations, and branches are useful shared records. A disproven hypothesis may be recorded successfully even when a proposal is rejected, a tool call fails, or the host cannot receive a result; those are separate lifecycle outcomes.

Red execution also requires a different trust regime: separate identities, planning and execution separation, explicit approval models, isolated environments, tool- and parameter-level policy, network restrictions, rate limits, audit, and blast-radius controls. The Red agent orchestrates bounded offensive tooling; it is not granted an unrestricted offensive toolbox. Blue and Green may use different policies and execution environments even while all three participate through the same semantic and proposal boundaries.

A coordinating agent is posture-neutral. It sequences declared work, passes schema-validated records, and maintains goal context, but it does not become an implicit superuser or inherit every participant’s permissions. Coordination is a responsibility; permissions are granted separately.

Structured handoff, not a shared workflow. Red-to-Blue transfer commonly takes the form of a narrative, attack-path analysis, evidence package, timeline, or detection-gap assessment. These records can have schemas, stable IDs, and source references while retaining the interpretation and human judgment that a rigid procedural API would erase.

8. Data Plane and Control Plane

The shared interaction runtime provides the data plane. It carries domain state, evidence, structured records, proposals, workflow state, approval events, validated action requests, results, and audit history. The control plane determines who and what may participate.

Agent-to-agent invocation is explicit, limited delegation. The caller may delegate only a permitted capability for a declared purpose and scope; the callee receives no implicit access from the caller or orchestrator. Iteration count, campaign duration, or exploratory depth never increases permissions. Agent creation is a control-plane and authoring operation. A runtime agent may propose a role, workflow, or policy record, but it cannot create or grant identity, credentials, tools, permissions, or policy activation. A proposed policy is evaluated under already-active policy and cannot authorize itself.

A person may inspect, amend, reject, approve, pause, redirect, resume, or revoke when policy permits. Each intervention becomes a validated audit event. The person, authorization service, and execution host all evaluate the same structured proposal.

10. Focused Validation Scenarios

The architecture is not based on a single product workflow. Existing scenarios test the design rules against different domains and runtime configurations:

Tiered Interaction

Portfolio and incident data can be transformed independently from the UI and service provider that use it.

Incident Exploration

Verdicts, attack paths, timelines, entities, indicators, and actions preserve source facts across narrative, sequence, and canvas views.

Governed SOC Work

Evidence, recommendation, human decision, approved request, external action, and result remain connected in one audit trail.

Operational Postures

Red exploration, Blue investigation and defense, and Green remediation exchange durable domain records while retaining different workflows, execution controls, roles, and permissions.

Validation criterion. Domain IDs, facts, allowed actions, and audit links must remain stable when the participant, provider, UI, transport, or permission grant changes independently.

11. Adoption Plan

  1. Start with domain contracts. Define domain records, evidence, relationships, source references, and valid outcomes before selecting screens or tools.
  2. Separate domain data from UI. Let agents return schema-validated data and let host code choose the runtime interaction.
  3. Establish one state and event model. Expose role-specific views for humans, agents, administrators, and headless hosts.
  4. Separate proposal from application. Give agents understanding and proposal operations while trusted hosts own authorization, admission, disposition, application, receipts, and audit.
  5. Make authority independently testable. Model identity, grants, delegation, approval eligibility, policy activation, services, and lifecycle in the control plane.
  6. Isolate external work. Keep credentials and external execution in trusted host handlers behind validation, timeouts, and limits.
  7. Test substitutions. Change the UI, provider, participant, or posture independently and verify that domain data, permissions, and audit history remain correct.

Conclusion

A trustworthy human-agent system is not a collection of agents attached to a user interface. It is a governed architecture with one authoritative state model, schema-validated domain data, reproducible rendering, explicit permissions, and controlled external execution.

Agents provide structured domain data. Declarative contracts define allowed types and transformations. The runtime owns interaction state. The control plane governs participation and delegation. Trusted hosts execute external work behind validation and policy. Humans and agents use different views of the same process, with an audit trail from goal to data, UI, decision, action, and result.
