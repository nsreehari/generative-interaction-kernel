A Governed Interaction Architecture for Human-Agent Systems

From agent-produced semantic constructs to validated UI and controlled execution · Technical position paper · 2026
Thesis. Humans and agents should use one governed interaction architecture instead of separate application paths. Agents produce schema-validated semantic constructs; host code renders, routes, persists, or governs those constructs; every participant receives a role-appropriate view of the same authoritative state; and a separate control plane determines who may view, propose, delegate, approve, or execute.

1. Separate Human and Agent Application Models

Most agentic systems give humans and agents different application models. Humans receive screens, forms, dashboards, and approval dialogs. Agents receive prompts, APIs, tools, and loosely structured context. Each path develops its own representation of state, available action, progress, and policy. A recommendation described in prose may not correspond to an executable operation; an API call may bypass the interaction contract visible to a human; and generated presentation may imply meaning the runtime cannot enforce.

Adding orchestration does not close this split. Passing text among agents coordinates conversation, but it does not define shared schemas, valid state changes, or permissions. The system needs one state and event model so that the same request maps to the same operation whether it comes from a person, an agent, or an API.

One authoritative state; closed domain schemas; validated transformations; role-specific views; explicit permissions; auditable external actions.

2. From Generated Responses to Semantic Composition

These models make different engineering tradeoffs. Agent-User Interaction (AG-UI) protocols can turn an agent response into interactive components, making complex data easier to inspect and act on than prose alone. A semantic layer solves a separate problem: it maps source data into stable domain records, relationships, requests, work items, and action proposals that screens, agents, and services can interpret consistently. The key design choice is the contract that crosses the agent-host boundary: prose, UI instructions, a fixed template, or validated semantic data.

4. Extending the Agent Semantic Vocabulary for Human Interactions

Human interaction needs no new agent mechanism. The host extends the same closed semantic vocabulary from Section 2 with typed interaction requests.

Agents produce requests for clarification, choice, and review through the same validation path as findings, evidence, and other domain data.

Semantic constructAgent providesHost policy and handling
ClarificationRequestMissing information · reason · response schemaChoose responder and channel · limit disclosure · timeout or resume
ChoiceRequestValid options · tradeoffs · decision contextVerify options · route to an authorized participant · normalize selection
ReviewRequestDraft output · review question · acceptance criteriaChoose qualified reviewer · collect feedback · return revision status
GenericRequestDeclared purpose · context · response schemaUse only when no specific request fits · validate and route without added authority

The request is channel-neutral. The host can render it with semantic components in the product UI, project it as a Microsoft Teams Adaptive Card, or deliver it through another approved interaction mechanism. Every channel returns the declared response type; channel-specific payloads do not enter agent reasoning. This is agent-initiated HITL: the agent requests human input needed to continue its work.

5. Extending the Agent Semantic Vocabulary for Product Workflow Participation and Actions

Product participation needs no new agent mechanism. The host extends the same semantic vocabulary with typed proposals for work, workflow transitions, and consequential actions.

Agents create these proposals through the same validation path as other semantic constructs. The host evaluates identity, permissions, current state, risk, and policy, then auto-admits, requests human approval, rejects, or expires the proposal.

Semantic constructAgent providesHost policy and handling
TodoProposalFollow-up work · priority · dependenciesAssign ownership · deduplicate · persist and track
WorkflowTransitionProposalTarget · requested transition · rationale · revisionCheck permissions and current state · admit or reject transition
ContainEndpointProposalTarget · evidence · rationale · expected impactAuto-approve · require human approval · reject or expire · execute if admitted
GenericProposalDeclared purpose · payload schema · rationaleUse only when no specific proposal fits · never bypass admission or execution policy

Policy-required HITL guards workflow actions. The host presents an approval request through the same interaction mechanisms from Section 4, records the authorized response, and revalidates the proposal and target revision before execution. Human approval does not grant the agent direct authority or bypass host admission.

One semantic vocabulary and one host policy pipeline provide a simpler shared architecture: agents propose, policy selects automation or human approval, and the host applies admitted work.

6. One Shared Substrate for Multiple Human and Multiple Agent Participation

Humans and agents do not coordinate by exchanging separate copies of context. They participate through governed views of the same authoritative semantic state.

The records, interaction requests, proposals, approvals, and results from Sections 2–5 become shared state and validated events. Each participant sees the permitted view for its role and contributes through the same event boundary.

Runtime contract. applyEvent(state, event) → { state, effectRequests }

Views do not duplicate the application or add authority. Human and agent events pass through the same schema and permission checks; admitted external work runs through host-owned handlers, and validated results return to shared state.

Handoffs between Red, Blue, Green Agents update shared state

Agent collaboration should not reduce to one agent posting a large message for another to interpret. Reports, narratives, attack paths, evidence packages, timelines, hypotheses, and failed attempts are structured work products in the shared data flow. Agents update them while working, so another agent can inspect provenance, uncertainty, prior work, and open questions without reconstructing context from conversation history.

Humans can inspect or render the same work products when visibility, judgment, or intervention is needed. The underlying artifacts remain shared semantic state: an extensible, validated contract for both agent continuity and human participation.

Shared state carries context, not authority. Agent-to-agent delegation is explicit and limited to a permitted capability, purpose, and scope; the receiving agent gains no implicit access from the caller or orchestrator. Agents may propose roles, workflows, or policy records, but cannot grant identity, credentials, tools, permissions, or policy activation to themselves or others. Human interventions are likewise validated and recorded as audit events.

A handoff changes who participates in the work; it does not create a second copy of context.

7. Typed Tiers and Governed Transformations

The architecture does not require six fixed layers. A Blueprint declares a finite ordered chain of N typed semantic tiers and N−1 transformation recipes. Tier names, schemas, granularity, and accepted source forms belong to the authored profile. The profile preserves distinctions that matter for a domain; it does not add layers merely to satisfy a platform pipeline.

The six-tier stack below is one illustrative profile for work that benefits from preserving intent, durable activity, workflow, shared interaction state, participant access, and runtime outcome as distinct contracts. Every arrow is a governed transformation boundary. A deterministic recipe, a selected strategy, a human compiler, or a model-assisted compiler may produce the next candidate, but that candidate must satisfy the target tier contract before it becomes authoritative.

Durable service profile implemented
Terminal Blueprint → portable materialization → journaled transitions → queued effect settlement. No presentation tier is required when the host is an API, middleware process, or durable worker.

Current Blueprint materialization accepts any authored chain that is connected, linear, and non-branching. It resolves the recipes in order, emits one validated terminal Blueprint, and then prepares the Kernel program. “Arbitrary tiers” therefore means that the platform does not prescribe the count or names; it does not mean that a running materialization creates tiers recursively or changes the chain dynamically.

A terminal Blueprint may omit projections.presentation. Its Cell events, reactions, computations, and source refresh behavior then compile into a headless Kernel program for APIs, middleware, and durable workers. Rendering hosts require a presentation explicitly; hosted child Blueprints also remain projection-hosted. Presentation is therefore a host capability rather than a universal execution dependency.

Natural language and model-assisted transformation

Natural language may accompany any tier as source, rationale, evidence, or provenance, but it should be authoritative input only where interpretation is an explicit part of the tier contract. Intent and exploration may be natural-language-first. Activity, workflow, and shared work products are often hybrid: typed structure carries identity and lifecycle while narrative carries rationale, uncertainty, and evidence. Policy, authorization, service contracts, effects, durable state, and executable programs remain typed.

A model may extract typed intent from a request, elaborate activities, propose workflow branches, select a compatible strategy, or synthesize a candidate recipe. At later boundaries it should normally transform typed input into typed output rather than reinterpreting the system from prose. The source language remains attached for traceability; it does not become executable authority.

source → typed candidate → validate & admit → approve when required → pin artifact → deterministic execution

An admitted model-assisted result should be pinned with its source and target tier identities, schema versions, provider and model identity, input and output hashes, relevant context and policy versions, validation results, and approval receipt. Subsequent execution consumes that accepted artifact; it need not ask a model to reinterpret the same decision on every run.

Today, normal materialization is synchronous and deterministic: materialize(authoredBlueprint, immutableContext) → terminalBlueprint. Recipes apply declared vocabulary patches or select pre-authored, contract-compatible representations and Cell programs from immutable context. Kernel-executed compiler Blueprints have separately demonstrated transforms, service-backed strategy work, validation, human confirmation, and artifact emission. Connecting those richer agent or human compiler pipelines to normal recipe chains is the extension point; their accepted outputs should become authored inputs to the deterministic path.

Examples

Incident investigation
A model preserves the source request while proposing typed goals, evidence activities, branches, and handoffs. The target schemas reject malformed structures, policy limits tools and delegation, and a human approves consequential changes. The accepted workflow is pinned before agents execute it.

Portfolio tracker
The projected profile uses immutable context to select among six participant representations; the sibling headless profile emits no presentation. Both select live HTTP or deterministic-agent market-data programs while seven stable Cells retain their contracts. No model interpretation is needed because the authored domain and implementation choices are already typed.

Durable backend work
The same state and event model runs without a mounted renderer, survives worker boundaries, settles effects idempotently, and can later expose state through UI, MCP, an API, or another transport. Headless execution changes the host medium, not the semantic contract.

A transformation provider may add interpretation; it never adds authority. Every emitted artifact remains a proposal until the target contract and active host policy admit it.

8. Multi-Agent Operational Postures

Multi-agent composition benefits from distinguishing how a participant approaches a problem from what it can do and what it is authorized to do. Red, Blue, and Green are useful generalized operational postures:

Red · Challenge and discover

Adopts an adversarial perspective, tests assumptions, explores exposure, and establishes whether a weakness is reachable or exploitable.

Blue · Understand and defend

Observes, classifies, correlates, investigates, explains, detects, and recommends defensive response from available evidence.

Green · Improve and restore

Prioritizes corrective change, proposes hardening and remediation, reduces exposure, and measures restored resilience.

The postures form a governed learning loop: challenge reveals pressure, observation establishes meaning, and improvement changes the system before it is challenged again. They are not security privileges and need not be permanent identities. A participant may adopt one or more postures for a bounded goal.

Red is not merely a Blue workflow with adversarial prompts

In security systems, Red frequently becomes a distinct operating class. Blue work commonly begins with known signals such as alerts, incidents, telemetry, vulnerabilities, or posture findings and follows bounded investigative or defensive tasks. Red work searches for what defenders do not yet know. It is iterative and exploratory: observe, form a hypothesis, test it, record the result, and choose the next test. It may run for extended periods, branch across possible attack paths, combine individually minor weaknesses, and produce no confirmed finding.

This distinction belongs primarily to the domain and activity model. A Red agent can use an adaptive specification to add hypotheses and attack-path branches as it explores. The dependency graph tracks the desired end state and missing prerequisites. The consequence graph identifies newly available work as facts are established. The exploratory graph selects, tests, and backtracks across alternative hypotheses. Accepted additions and results enter shared state, allowing humans and Blue or Green participants to inspect the same investigation through their own role-specific views.

That autonomy is limited by the domain schema and active policy. It does not require storing every internal thought, and it does not move offensive execution into the graph. The contract decides which hypotheses, attempts, observations, and branches are useful shared records. A disproven hypothesis may be recorded successfully even when a proposal is rejected, a tool call fails, or the host cannot receive a result; those are separate lifecycle outcomes.

Red execution also requires a different trust regime: separate identities, planning and execution separation, explicit approval models, isolated environments, tool- and parameter-level policy, network restrictions, rate limits, audit, and blast-radius controls. The Red agent orchestrates bounded offensive tooling; it is not granted an unrestricted offensive toolbox. Blue and Green may use different policies and execution environments even while all three participate through the same semantic and proposal boundaries.

A coordinating agent is posture-neutral. It sequences declared work, passes schema-validated records, and maintains goal context, but it does not become an implicit superuser or inherit every participant’s permissions. Coordination is a responsibility; permissions are granted separately.

10. Focused Validation Scenarios

The architecture is not based on a single product workflow. Existing scenarios test the design rules against different domains and runtime configurations:

Tiered Interaction

Portfolio and incident data can be transformed independently from the UI and service provider that use it.

Incident Exploration

Verdicts, attack paths, timelines, entities, indicators, and actions preserve source facts across narrative, sequence, and canvas views.

Governed SOC Work

Evidence, recommendation, human decision, approved request, external action, and result remain connected in one audit trail.

Operational Postures

Red exploration, Blue investigation and defense, and Green remediation exchange durable domain records while retaining different workflows, execution controls, roles, and permissions.

Validation criterion. Domain IDs, facts, allowed actions, and audit links must remain stable when the participant, provider, UI, transport, or permission grant changes independently.

11. Adoption Plan

  1. Start with domain contracts. Define domain records, evidence, relationships, source references, and valid outcomes before selecting screens or tools.
  2. Separate domain data from UI. Let agents return schema-validated data and let host code choose the runtime interaction.
  3. Establish one state and event model. Expose role-specific views for humans, agents, administrators, and headless hosts.
  4. Separate proposal from application. Give agents understanding and proposal operations while trusted hosts own authorization, admission, disposition, application, receipts, and audit.
  5. Make authority independently testable. Model identity, grants, delegation, approval eligibility, policy activation, services, and lifecycle in the control plane.
  6. Isolate external work. Keep credentials and external execution in trusted host handlers behind validation, timeouts, and limits.
  7. Test substitutions. Change the UI, provider, participant, or posture independently and verify that domain data, permissions, and audit history remain correct.

Conclusion

A trustworthy human-agent system is not a collection of agents attached to a user interface. It is a governed architecture with one authoritative state model, schema-validated domain data, reproducible rendering, explicit permissions, and controlled external execution.

Agents provide structured domain data. Declarative contracts define allowed types and transformations. The runtime owns interaction state. The control plane governs participation and delegation. Trusted hosts execute external work behind validation and policy. Humans and agents use different views of the same process, with an audit trail from goal to data, UI, decision, action, and result.
